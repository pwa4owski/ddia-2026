# DDIA HW2 — стратегии устойчивости

Мини-фреймворк устойчивых обращений к воображаемому stateless-сервису. Реализованы шесть стратегий: default, retries, exponential backoff, round-robin, hedging и circuit breaking.

## Запуск

Требуются **JDK 25** и переменная `JAVA_HOME`, указывающая на него. Gradle 9.1.0 запускается через включённый Wrapper; зависимости загружаются автоматически.

Из каталога задания в Bash:

```bash
chmod +x gradlew test.sh
./test.sh
```

Скрипт выполняет `./gradlew --no-daemon clean test` и возвращает ненулевой код при ошибке компиляции или тестов. Полная сборка:

```bash
./gradlew --no-daemon clean build
```

В PowerShell доступны эквивалентные команды `./gradlew.bat --no-daemon clean test` и `./gradlew.bat --no-daemon clean build`.

Отчёт тестов: **`build/reports/tests/test/index.html`**. Внешний сервер для запуска не требуется: его поведение моделирует тестовый отправитель.

Стек: Java 25, Gradle Kotlin DSL, Spring Boot 4.1.1, Resilience4j CircuitBreaker 2.3.0, JUnit Jupiter 5.14.2.

## Архитектура и API

Основной пакет — `ru.ddia`. Транспорт, исполнение стратегии, учёт бюджетов и выбор endpoint разделены.

| Компонент | Ответственность |
| --- | --- |
| `SubrequestSender` | `send(Request)` начинает один асинхронный подзапрос; таймауты и сценарии не входят в аргументы |
| `SubrequestCall` | Предоставляет результат через `completion()` и явную отмену через `cancel()` |
| `SubrequestResult` | Типизированные исходы: `2xx` с payload, `4xx`, `5xx`, `Timeout` |
| `ResilienceClient<S>` | Выполняет стратегию с одним отправителем |
| `ResilienceMultiClient<S>` | Выполняет стратегию с упорядоченной коллекцией `Endpoints` |
| `OperationResult` | Успех со статусом и payload либо ошибка с причиной, числом отправок и последним исходом |
| `SequentialExecutor` | Общий цикл default, retries, backoff, round-robin и circuit breaking |
| `RetryDelayPolicy`, `EndpointSelector` | Подменяемые стратегии задержки и выбора отправителя |

Клиентский `execute()` синхронный. `send()` должен быстро возвращать handle, чтобы клиент мог ограничить ожидание и отменить вызов. Один экземпляр sender обслуживает один логический запрос и его подзапросы. Тела запроса и успешного ответа представлены строками.

Стратегии построены через композицию: например, round-robin использует тот же исполнитель и ту же политику backoff, что и клиент с одним отправителем. Hedging имеет отдельный цикл конкурентных завершений и использует общие транспортный API, модель результата и дедлайны.

Spring создаёт все шесть клиентов как beans. Библиотечные классы также можно использовать напрямую; примеры вызовов находятся в тестах.

## Поведение стратегий

| Стратегия | Реализация | Основное поведение |
| --- | --- | --- |
| Default | `DefaultClient` | Одна попытка с ограниченным временем ожидания |
| Retries | `RetryClient` | Последовательные повторы до первого успеха или исчерпания бюджета |
| Exponential backoff | `BackoffClient` | Повторы с растущими задержками после `5xx` и Timeout |
| Round-robin | `RoundRobinClient` | Каждый следующий подзапрос направляется на следующий endpoint по кругу |
| Hedging | `HedgingClient` | При задержке первого ответа конкурентно запускает остальные endpoint; возвращает первый успех |
| Circuit breaking | `CircuitBreakingClient` | Исключает деградировавшие endpoint из round-robin и проверяет восстановление после cooldown |

### Бюджеты, время и отмена

- `maxAttempts` — общее число отправок, **включая первую**; для default равно 1. Попытка учитывается непосредственно перед `send()`.
- Бюджеты `4xx`, `5xx` и Timeout независимы. Достижение лимита запрещает следующий повтор. Например, лимит 2 разрешает повтор после первой ошибки, но не после второй. Нулевой бюджет допускает первую попытку, но запрещает повтор после соответствующей ошибки.
- Повторы после `4xx` разрешены учебной моделью. Успех на последней разрешённой попытке возвращается нормально.
- Общий deadline отсчитывается от начала логического запроса и включает все попытки и паузы. В последовательных стратегиях ожидание попытки ограничено `min(subrequestTimeout, remainingGlobalTime)`.
- Перед отправкой и после ожидания проверяется deadline. Ответ на самой границе считается опоздавшим; после исчерпания времени новых отправок нет.
- Время измеряется монотонно через `Ticker` (`System.nanoTime()`); в тестах часы можно контролировать.
- Таймаут и прерывание прекращают ожидание и вызывают `cancel()`. Прерывание передаётся вызывающему коду как `InterruptedException`. Отмена идемпотентна и выполняется best effort: уже выполненную удалённую операцию она не откатывает.

Причины ошибки различимы: `ATTEMPTS_EXHAUSTED`, `FAST_ERRORS_EXHAUSTED`, `FAILURES_EXHAUSTED`, `TIMEOUTS_EXHAUSTED`, `DEADLINE_EXCEEDED`, `NO_HEALTHY_ENDPOINTS`. При одновременном исчерпании бюджетов приоритет имеет общий deadline, затем число попыток, затем категория ошибки. Исход последнего подзапроса сохраняется.

Пустой список endpoint, повторяющиеся ID, `null`, некорректные статусы и недопустимые бюджеты отклоняются. Один endpoint допустим. Интервалы должны помещаться в `long` наносекунд. Неожиданное исключительное завершение транспорта считается нарушением его контракта и приводит к `IllegalStateException` с исходной причиной.

### Backoff и round-robin

Задержка рассчитывается как `min(maxDelay, initialDelay × multiplier^k)`, где `k = 0, 1, …`, `multiplier > 1`. Последовательные `5xx` и Timeout образуют общую серию. После `4xx` задержки нет, серия сбрасывается. После успеха или исчерпания бюджета паузы нет. Расчёт защищён от переполнения, дробные наносекунды округляются вниз; jitter не используется.

Round-robin начинает каждый логический запрос с первого endpoint: `A → B → C → A`. Порядок входного списка сохраняется. Бюджеты и серия backoff общие для запроса и не сбрасываются при смене endpoint. В `RoundRobinSettings` можно передать `ExponentialBackoff` как политику задержки; по умолчанию повторы немедленные.

Счётчики попыток и курсор ротации принадлежат запросу. Совместное использование клиента не смешивает состояние запросов; внедряемые часы, sleeper и пользовательские политики при этом должны быть потокобезопасными.

### Hedging

`HedgingSettings` содержит только общий таймаут и `hedgingDelay` — бюджетов категорий ошибок здесь нет.

Первый подзапрос направляется на первый endpoint. Если до `hedgingDelay` успеха нет и вызов ещё выполняется, остальные неблокирующие `send()` запускаются без ожидания их ответов. На каждый endpoint приходится не более одной отправки. Быстрый первый успех не запускает остальные вызовы; после раннего отказа первого остальные запускаются сразу.

Победитель — первый успешный `2xx`, даже если ранее другой endpoint вернул ошибку. При успехе, deadline или прерывании handles отменяются, поздние результаты игнорируются. Если все endpoint ответили ошибками, клиент ожидает общего deadline без новых отправок и активного опроса. `hedgingDelay = 0` допустим.

### Circuit breaking

Resilience4j ведёт окно последних **N** результатов на endpoint. `4xx`, `5xx` и Timeout считаются ошибками. Цепь открывается на заполненном окне при строгом `errors / N > threshold`.

| Состояние | Поведение |
| --- | --- |
| CLOSED | Endpoint участвует в ротации, результаты попадают в окно |
| OPEN | Endpoint пропускается в течение cooldown **T** |
| HALF_OPEN | После T допускается одна проба; успех закрывает цепь и очищает историю, ошибка снова открывает её на T |

`CircuitSettings` фиксирует N, threshold и T на время жизни клиента. Spring bean использует `N = 10`, `threshold = 0.5`, `T = 5 секунд`. На каждый запрос передаются `RoundRobinSettings` с бюджетами и необязательным backoff.

В Resilience4j сравнение порога нестрогое (`>=`), поэтому адаптер находит первое число ошибок, для которого `errors / N > threshold`, и устанавливает процентную границу между ним и предыдущим значением. При расчёте учитывается округление дробного порога. При `threshold = 1` используется METRICS_ONLY: доля ошибок не может превысить 100%.

Cooldown отсчитывается монотонным `Ticker`. Разрешение пробы освобождается при прерывании, а поколения цепи не позволяют позднему ответу старого вызова повлиять на новую пробу. Изменение состояния синхронизировано на endpoint; ожидание транспорта происходит вне блокировки.

Реестр принадлежит экземпляру клиента и использует **стабильный endpoint ID**, поэтому история сохраняется при создании новых sender. Предполагается ограниченный набор ID; автоматического удаления записей нет. Если все endpoint недоступны, возвращается `NO_HEALTHY_ENDPOINTS` без ожидания и без расходования новой попытки.

Границы бюджетов, сброс серии backoff после `4xx`, ранний запуск хеджей после отказа и правила HALF_OPEN — инженерные соглашения, уточняющие неоднозначные места условия.

## Тесты

Тесты находятся в [`src/test/java/ru/ddia`](src/test/java/ru/ddia). `ScriptedFakeSender` моделирует ответы, задержки и зависание; журнал фиксирует фактические отправки, их порядок и отмену. Проверяются результат операции и наблюдаемое поведение отправителей.

Покрытие распределено по ответственности: общие бюджеты и последовательное выполнение проверяются в default/retries, задержки — в backoff, а выбор endpoint и сочетание с backoff — в round-robin. Общий `SequentialExecutor` позволяет не повторять одинаковые проверки для каждого клиента. Для конкурентного hedging и состояния circuit breaker сохранены отдельные проверки гонок, отмены и точных временных границ.

| Набор | Число случаев | Основные проверки |
| --- | ---: | --- |
| Default | 12 | Payload, ровно одна отправка, ошибки, таймаут и отмена |
| Retries | 17 | Повторы после отказов, независимые лимиты, последовательность, общий deadline |
| Backoff | 9 | Рост задержек, остановка повторов и пауз, ограничение deadline и защита от переполнения |
| Round-robin | 9 | Порядок и замыкание круга, общие бюджеты, backoff со сбросом после `4xx`, независимость запросов |
| Hedging | 11 | Конкурентность, первый из двух успехов, граница задержки, все ошибки, отмена |
| Circuit breaking | 12 | Строгий порог и округление, вытеснение ошибок из окна, граница cooldown, одна проба, поздние ответы |
| API, время, Spring | 10 | Валидация, границы времени и выполнение всех шести клиентов из Spring-контекста |

Всего **80 тестовых случаев**, включая параметризованные. Для границ времени используются управляемые часы, для конкуренции — futures и синхронизация. Реальные таймауты дополнительно проверяют цепочку «зависание → таймаут → отмена → открытие circuit breaker».
